Week-by-week learning plan

Month 1 Sharpen Foundations

Theme: Fill the critical gaps in your existing backend knowledge. No new frameworks yet — master what you already know, then add auth and testing.

Week 1 Node.js internals + Express mastery ▶
// Node.js core
  • Event loop — phases: timers, poll, check; why it matters for async code
  • Blocking vs non-blocking I/O — when sync code stalls your server
  • Streams — readable, writable, transform; streaming large files without memory crash
  • Buffer and fs module — reading files, working with binary data
  • process.env and config management — dotenv, environment variables best practices
  • Module system — CommonJS vs ESM, circular dependencies

// 05 · interview prep

Questions you will actually be asked

Click any question to see how to answer it. These are real questions from Indian backend interviews at startups and product companies.

NODEExplain the Node.js event loop. What happens when you use a blocking operation?
Node.js is single-threaded. The event loop processes callbacks in phases: timers (setTimeout), I/O callbacks, idle/prepare, I/O poll, setImmediate, and close callbacks. When you call a non-blocking I/O operation (like reading a file), Node delegates it to libuv, continues executing other code, and processes the result callback only when the I/O completes. If you call a blocking operation (like fs.readFileSync), it freezes the entire thread — no other request can be handled until it completes. This is why you always use async versions of I/O functions in production Node.js.
AUTHHow do access tokens and refresh tokens work? Why do we need both?
Access tokens are short-lived (15–30 minutes) JWTs that authenticate API requests. Refresh tokens are long-lived (7–30 days) tokens stored securely and used only to get new access tokens. We need both because: if an access token is stolen, it expires quickly (15 min). If we only had one long-lived token, theft means the attacker has access for days. The refresh token should be stored in an httpOnly cookie (inaccessible to JavaScript) and sent only to a single /refresh endpoint. On logout, we blacklist the refresh token in Redis so it can't be used even before it expires.
DBWhat's the difference between SQL and NoSQL? When do you choose each?
SQL (PostgreSQL): structured data with defined relationships, ACID transactions, complex queries with JOINs. Best for: financial data, user accounts, anything with strict consistency requirements. NoSQL (MongoDB): flexible schema, document-oriented, horizontal scaling. Best for: product catalogs (attributes vary per product), content platforms, data where structure changes frequently. In practice at Indian startups: use PostgreSQL for your user/auth/payment data (correctness matters most) and MongoDB for your content/catalog/event data (flexibility matters most). Avoid picking one just because it's trendy — pick based on your data's shape and consistency needs.
DBWhat is a database index? What's the trade-off?
An index is a separate data structure (usually a B-tree) that keeps a sorted copy of one or more columns, allowing the database to find rows without scanning the entire table. A query on an indexed column goes from O(n) scan to O(log n) lookup. The trade-off: indexes speed up reads but slow down writes (every INSERT/UPDATE/DELETE must update the index too) and consume extra disk space. Practical rule: always index foreign keys, columns used in WHERE/JOIN/ORDER BY clauses, and columns used in unique constraints. Don't index every column — tables with many indexes become slow on writes.
ASYNCHow would you handle sending 50,000 welcome emails without slowing down the API?
Never send emails synchronously inside an API handler — it blocks the response for 2–5 seconds and fails if the email server is down. Instead: the API endpoint adds a job to a BullMQ queue (Redis-backed) and immediately responds with 200. A separate worker process picks up jobs from the queue and sends emails one by one (or in small batches). Benefits: the API responds in milliseconds, failed emails retry automatically with exponential backoff, and the email throughput is controlled to avoid hitting rate limits. This is exactly what I built in my Job Queue project.
RESTWhat makes a good REST API design? Walk me through your approach.
Good REST design: (1) Resource-oriented URLs — nouns, not verbs. /users/:id not /getUser/:id. (2) Correct HTTP methods — GET to read, POST to create, PUT/PATCH to update, DELETE to remove. (3) Consistent response shape — always return { data, error, meta } so clients can rely on the structure. (4) Proper status codes — 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Validation Error, 500 Internal Server Error. (5) Versioning — prefix with /api/v1/ so you can introduce breaking changes in v2 without breaking existing clients. (6) Pagination on list endpoints — never return unbounded arrays. Always include page, limit, total in the response.
SCALEHow would you improve the performance of a slow API endpoint?
Systematic approach: (1) Identify the bottleneck first — is it slow SQL, N+1 queries, missing indexes, or no caching? Use EXPLAIN ANALYZE on the query. (2) Fix database issues — add indexes on WHERE/JOIN columns, batch N+1 queries, rewrite with proper JOINs. (3) Add caching — if the data doesn't change per-request, cache it in Redis with a TTL. (4) Paginate — if you're returning 10,000 rows, return 20 at a time. (5) Check for synchronous blocking operations — nothing blocking in the request handler. (6) If none of the above: profile with clinic.js or look at connection pool settings. I applied this in my projects by running EXPLAIN ANALYZE and cutting query time by adding compound indexes.
GITWhat's your Git workflow? How do you handle merge conflicts?
I follow a feature branch workflow: create a branch from main for each feature (feature/user-auth, fix/login-bug), make commits with clear messages (feat: add JWT refresh token), push the branch, open a pull request, get review, then merge. For merge conflicts: (1) git fetch origin main, (2) git rebase origin/main on my branch, (3) resolve conflicts in the editor by understanding both changes and deciding what the correct final state should be, (4) git add the resolved files, (5) git rebase --continue, (6) push with --force-with-lease. I also write commit messages in conventional commits format (feat/fix/chore/docs) so the history is readable.
